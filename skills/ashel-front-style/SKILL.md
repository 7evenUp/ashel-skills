# Ashel Front Style

Авторские соглашения Ashel для React/TypeScript: смысловые группы импортов и состояний, конкретные имена, небольшие компоненты, прямые обработчики и видимые состояния интерфейса.

Перед изменениями учитывай инструкции целевого проекта, версии зависимостей, настройки ESLint/Prettier, архитектуру и существующие соглашения. Сохраняй публичные контракты и выбранный стек. Если пользователь явно не просит изменить соглашения, правила проекта имеют приоритет над предпочтениями этого skill. Применяй следующие решения по умолчанию в новом проекте или там, где соглашения ещё не заданы; не переформатируй несвязанный код. Упомянутые библиотеки не являются обязательным списком зависимостей.

## Импорты и оформление

Разделяй смысловые группы импортов пустой строкой.

Группируй: React и сторонние библиотеки; ассеты; компоненты; API и состояние; типы; утилиты. Соседние импорты одной сущности держи вместе, не отделяй пустой строкой каждую строку. Импорты стилей располагай последними. Смысловая группировка важнее ручной алфавитной сортировки всего списка, если проект не задаёт другой порядок.

```tsx
import { useState } from "react"
import { toast } from "sonner"
import { useTranslation } from "react-i18next"

import Input from "./Input"
import Button from "./Button"

import { useCreateModuleMutation } from "./moduleApi"

import type { Module } from "./types"

import { cn } from "./cn"
```

Используй относительные импорты для локальных соседей. Для общих модулей подходит `@/`, если alias уже настроен в проекте.

Если форматтер проекта не задаёт другое: TS/TSX — два пробела, двойные кавычки, без точек с запятой, trailing commas — `es5`; длинные списки аргументов и JSX-пропсов переноси на отдельные строки. Не меняй конфигурацию форматирования ради локальной задачи.

## Компоненты, пропсы и имена

- Обычный компонент объявляй как `const Name = (...) => { ... }`, деструктурируй пропсы в аргументе, заверши `export default Name`. Для общего UI-примитива или группы связанных exports используй именованные экспорты. Не переделывай существующий публичный экспорт без задачи.
- Маленькую форму пропсов пиши прямо в аргументе. Для больших или повторно используемых пропсов выделяй `NameProps`. Не добавляй `React.FC` и тип возвращаемого JSX по шаблону.
- Данные, payload и ответы описывай предметными `interface`/`type`; для конечных состояний используй строковые unions. Не вводи обязательный префикс `I` или `T`. Используй `import type` для типов.
- Имя показывает роль: `ReferralItem`, `CreateModule`, `ProfileActions`, `TasksLoadingScreen`. Избегай неинформативных `Manager`, `Controller`, `Wrapper` без конкретной обязанности.
- Boolean-состояния называй `isOpen`, `isLoading`, `hasChanges`; выбранные значения — `selectedId`, `activeStep`. Различай результаты запросов: `data: profileData`, `isLoading: isProfileLoading`.
- Обработчик называй по действию: `handleSubmit`, `handleItemClick`, `onSubmit`, `toggleTheme`. Логику держи в именованном обработчике; короткое изменение одного поля можно оставить в JSX.
- Код и идентификаторы — на английском. Комментарии объясняют причины и предметные ограничения; язык комментария соответствует языку команды. Не пересказывай очевидный JSX.

```tsx
const UserNickname = ({ nickname }: { nickname: string }) => {
  return <span className="truncate text-sm font-medium">{nickname}</span>
}

export default UserNickname
```

## Структура и расположение логики

### Структура папок и границы ответственности

Группируй код по экрану или самостоятельному пользовательскому сценарию. Компоненты, формы, модалки и hooks, используемые только внутри этого сценария, храни рядом с ним. По расположению файла должно быть понятно, к какой части приложения он относится.

Пример структуры приложения:

```text
src/
  app/
    App.tsx
    router.tsx
    Providers.tsx

  pages/
    Profile/
      Profile.tsx
      components/
        ProfileHeader.tsx
        ProfileActions.tsx
      modals/
        UpdateEmail/
          UpdateEmail.tsx
          components/
            EmailForm.tsx
            VerificationForm.tsx
      hooks/
        useProfileForm.ts

  components/
    Header/
      Header.tsx
      components/
        Navigation.tsx
        AccountMenu.tsx

  shared/
    ui/
      Button.tsx
      Input.tsx
      Dialog.tsx
      Skeleton.tsx

  api/
    core.ts
    profile.ts

  store/
    index.ts
    hooks.ts

  types/
    user.ts

  utils/
    formatDate.ts

  lib/
    cn.ts

  assets/
    icons/
    images/
```

- `app` соединяет приложение: маршруты, providers и корневую композицию.
- `pages` содержит экраны и принадлежащие им части.
- Корневая `components` содержит общие предметные компоненты, например шапку.
- `shared/ui` содержит переиспользуемые UI-примитивы без привязки к конкретному экрану.
- `api` содержит запросы и настройку транспорта.
- `store` общее клиентское состояние.
- `utils` содержит самостоятельные функции преобразования данных.
- `lib` небольшие вспомогательные интеграции и настройки библиотек.

**Внутренняя папка `components` принадлежит своему родительскому блоку.** Храни в ней компоненты, относящиеся к одной сущности, экрану или сценарию, которые не имеют самостоятельного назначения в остальном приложении. Например, `EmailForm` и `VerificationForm` принадлежат `UpdateEmail`, а `Navigation` и `AccountMenu` — `Header`.

Такие компоненты могут использоваться несколькими частями родительского блока и при этом оставаться локальными. Повторное использование внутри одной сущности само по себе не является причиной переносить компонент в корневую `components` или `shared/ui`. Переноси его в общую область, когда появляется самостоятельная ответственность и реальная потребность за пределами родительского блока.

Это ориентир, а не обязательный каркас. Создавай папки по мере появления кода. Если используется маршрутизация на основе файлов, сохраняй требуемую ею структуру.

Не переноси локальный компонент в общую папку только потому, что он называется Button или Card. Кнопка покупки с предметной логикой остаётся рядом со своим сценарием; универсальная кнопка с оформлением и нативными props подходит для `shared/ui`.

Типы, константы и helpers одного компонента могут оставаться в его файле. Выноси их в соседние `types.ts`, `constants.ts` или `utils.ts`, когда они используются несколькими локальными частями или мешают читать основной компонент.

Общие модули не должны импортировать детали конкретной страницы. Страница собирает общие компоненты и локальные блоки; UI-примитив не знает, какая страница его использует.

### Расположение логики

Для лендинга используй композицию секций: `sections/Hero/Hero.tsx`, `sections/Benefits/Benefits.tsx`, затем явно перечисли их в странице. Не строй JSON-конструктор ради одной страницы. Не создавай цепочку container/view/controller/service без практической необходимости.

Внутри компонента организуй hooks, данные и обработчики в смысловые блоки. Не собирай все объявления одного технического типа в сплошной список: порядок определяется связями между частями сценария. Hooks вызываются безусловно, до любых условных выходов из компонента. Небольшая функция или декоративный SVG может оставаться в том же файле; повторяющиеся данные и самостоятельные части UI выноси отдельно.

Локальную форму, открытие модалки и временный шаг держи в `useState`. Общий UI-state — в общем хранилище, серверные данные — в query-кэше, когда он используется в проекте. Не дублируй ответ сервера в state без задачи редактирования draft. Используй прямые `map/filter/reduce`; `useMemo/useCallback` добавляй для стоимости расчёта или стабильности зависимости, а не к каждой операции. Если в проекте включён React Compiler, учитывай автоматическую мемоизацию перед добавлением ручной.

## Группировка состояний и поведения

Разделяй `useState` пустыми строками по назначению. Поля одной формы держи вместе; шаги, открытие диалога или другой самостоятельный UI-сценарий отделяй. Внутри формы тоже могут быть группы: название с описанием отдельно от часов с минутами.

```tsx
const [isSecondStep, setIsSecondStep] = useState(false)

const [oldEmailInput, setOldEmailInput] = useState("")
const [newEmailInput, setNewEmailInput] = useState("")
```

Граница проходит по смыслу, а не по типу значения. Поле и ошибка конкретного способа входа могут составлять одну группу, данные другого способа — другую. Не выноси все boolean в отдельную секцию только потому, что они boolean. Не отделяй пустой строкой каждый hook и не добавляй комментарии-заголовки к очевидным парам состояний.

Сохраняй отдельные `useState` для независимых значений. Визуальная группировка не требует объединять их в объект или вводить reducer только ради уменьшения числа hooks. Общее обновление и переходы состояний, а не количество строк, определяют необходимость другой модели.

- Состояние, ref, производное значение и короткий обработчик одного сценария могут находиться рядом. Все hooks остаются на верхнем уровне компонента, вне условий и обработчиков. Не вводи фиксированный порядок всех разновидностей hooks.
- Отделяй группу selectors от связанных query-hooks; mutations одного действия или группы действий держи вместе. Используй предметные алиасы для `data`, `isLoading`, `refetch`, `reset`, если рядом несколько запросов.
- Парные действия `openSecondStep/closeSecondStep`, `handleOpen/handleClose` держи рядом. Переход между шагами и сброс формы — отдельные намерения, не одна универсальная toggle-функция.
- Повторяемый набор сбросов выноси в `resetState`, `clearState` или предметный `resetAuthVariant` и вызывай из соответствующих переходов. Внутри сброса также разделяй разные группы пустой строкой. Сбрасывай только нужные значения; данные, необходимые следующему шагу или повторной попытке, сохраняй.
- Разные внешние процессы оформляй отдельными эффектами: таймер, DOM/SDK-подписка, синхронизация с внешним источником. Не объединяй несвязанные эффекты из-за одинакового массива зависимостей; не дроби единый процесс так, чтобы потерять его cleanup.
- В JSX разделяй пустыми строками самостоятельные блоки: заголовок, поля формы, сообщения, действия, отдельные модалки. Связанные элементы одного поля держи вместе, чтобы логика группировки сохранялась и в разметке.

## UI и стили

Для прикладного UI предпочитай Tailwind в JSX. Объединяй классы через `cn = twMerge(clsx(...))`: базовые классы → условные классы/варианты → внешний `className`. Потребитель компонента должен иметь возможность переопределить оформление.

```tsx
className={cn(
  "flex items-center gap-3 rounded-xl p-3",
  isSelected && "bg-black text-white",
  isDisabled && "opacity-50",
  className
)}
```

Простые варианты оформляй явными условиями; устойчивую матрицу `appearance/size` можно вынести в CVA. Не вводи фабрику вариантов ради одной карточки. Для точного макета допустимы arbitrary values, градиенты, отдельные декоративные слои и inline SVG. Цвета, шрифты и размеры определяются интерфейсом, а не этим skill. Не собирай Tailwind-классы динамической строкой вроде `bg-${color}`.

Нативные UI-обёртки расширяй `ComponentProps`/`HTMLAttributes`, пробрасывай `...props`, `children`, `className` и ref, если он нужен API. Способ передачи ref выбирай по версии React в проекте.

Диалоги, вкладки и переключатели собирай через Base UI или готовые примитивы, если они доступны. Состояние открытого / раскрытого примитива выражай через локальный state `open/onOpenChange`, если требуется программно оперировать примитивом; Если примитив требуется открывать / раскрывать из разных частей приложения, стоит создать глобальную переменную-состояние (например slice, если в качестве стора используется redux-toolkit).

Адаптивные значения задавай для нужных переходов макета; не копируй фиксированный набор breakpoints в каждую задачу. Учитывай safe area там, где это нужно интерфейсу. Анимации добавляй по задаче и учитывай `prefers-reduced-motion` для очень сложных анимаций, включая skeleton-анимации.

## Запросы, формы и состояния

- Если используется RTK Query, группируй endpoints по предметной области, расширяй базовый API через `injectEndpoints`, типизируй `build.query/build.mutation`, экспортируй сгенерированные hooks. Tags отражают данные, которые нужно обновить после мутации. Если выбран TanStack Query/Axios, сохраняй этот подход без миграции ради стиля.
- Сохраняй точные поля серверного контракта, в том числе snake_case. Не добавляй промежуточный слой переименования без задачи.
- Асинхронное действие оформляй как guard при pending → подготовка/проверка данных → `await mutation(payload).unwrap()` → действия после успеха → `catch`. В TanStack Query для такого потока используй `mutateAsync` либо callbacks, соответствующие сценарию.
- Не допускай повторного действия во время запроса: pending guard и disabled на соответствующей кнопке. Закрывай диалог и очищай ввод после подтверждённого успеха, если сценарий не задаёт другой переход.
- Известным кодам ошибок сопоставляй предметный текст, остальным — понятный fallback. Ошибку типа `unknown` сужай по реальной форме ответа; не маскируй её `any`, неподтверждённым cast или `@ts-expect-error`.
- Для короткой формы достаточно controlled inputs и `useState`. Для сложной формы с валидацией подходит React Hook Form + Zod, `z.infer`, ошибки около полей. Не добавляй эти зависимости к каждому input.
- Loading, error, empty и success — отдельные состояния. Skeleton повторяет геометрию загружаемого блока; loader действия остаётся в кнопке. Не заменяй ошибку бесконечной загрузкой. При обновлении данных сохраняй уже полезный контент, когда это подходит сценарию.
