# Frontend Code Style

Пиши код, который легко просматривать глазами: смысловые группы импортов, конкретные имена, небольшие компоненты, прямые обработчики и видимые состояния интерфейса. Применяй правила сразу к задаче. Skill содержит все необходимые указания и примеры; предварительное чтение чужих инструкций, изучение репозиториев и поиск первоисточников не нужны.

При изменении кода сохраняй уже заданные публичные контракты и явно выбранный пользователем стек. В остальных случаях используй следующие решения по умолчанию. Правила описывают стиль кода, а не обязательный список зависимостей.

## Импорты и оформление

Разделяй импорты разных сущностей пустой строкой. Это визуально разбивает длинный список на смысловые блоки и помогает программисту быстрее находить нужную зависимость.

Группируй: React и сторонние библиотеки; ассеты; компоненты; API и состояние; типы; утилиты. Соседние импорты одной сущности держи вместе, не отделяй пустой строкой каждую строку. Импорт CSS/SCSS Module располагай последним. Смысловая группировка важнее ручной алфавитной сортировки всего списка.

```tsx
import { useState } from "react"
import { toast } from "sonner"
import { useTranslation } from "react-i18next"

import Input from "./Input"
import Button from "./Button"

import { useCreateModuleMutation } from "./moduleApi"

import type { Module } from "./types"

import { cn } from "./cn"
```

Используй относительные импорты для локальных соседей. Для общих модулей подходит `@/`, если alias уже предоставлен окружением. Alias не является обязательной зависимостью примеров.

TS/TSX: два пробела, двойные кавычки, без точек с запятой; длинные списки аргументов и JSX-пропсов переноси на отдельные строки. Для нового кода trailing commas — `es5`. В CSS/SCSS сохраняй точки с запятой. Не меняй конфигурацию форматирования ради локальной задачи.

## Компоненты, пропсы и имена

- Обычный компонент объявляй как `const Name = (...) => { ... }`, деструктурируй пропсы в аргументе, заверши `export default Name`. Для общего UI-примитива или группы связанных exports используй именованные экспорты. Не переделывай существующий публичный экспорт без задачи.
- Маленькую форму пропсов пиши прямо в аргументе. Для больших или повторно используемых пропсов выделяй `NameProps`. Не добавляй `React.FC` и тип возвращаемого JSX по шаблону.
- Данные, payload и ответы описывай предметными `interface`/`type`; для конечных состояний используй строковые unions. Не вводи обязательный префикс `I` или `T`. Используй `import type` для типов.
- Имя показывает роль: `ReferralItem`, `CreateModule`, `ProfileActions`, `TasksLoadingScreen`. Избегай неинформативных `Manager`, `Controller`, `Wrapper` без конкретной обязанности.
- Boolean-состояния называй `isOpen`, `isLoading`, `hasChanges`; выбранные значения — `selectedId`, `activeStep`. Различай результаты запросов: `data: profileData`, `isLoading: isProfileLoading`.
- Обработчик называй по действию: `handleSubmit`, `handleItemClick`, `onSubmit`, `toggleTheme`. Логику держи в именованном обработчике; короткое изменение одного поля можно оставить в JSX.
- Код и идентификаторы — на английском. Комментарии объясняют причины и предметные ограничения; язык комментария соответствует языку команды. Не пересказывай очевидный JSX.

```tsx
const UserNickname = ({ nickname }: { nickname: string }) => {
  return <span className="truncate text-sm font-medium">{nickname}</span>
}

export default UserNickname
```

## Структура и расположение логики

Храни компоненты конкретного экрана рядом с ним. Экран собирает предметные блоки; блоки могут иметь локальные `components`, `modals`, `hooks`, `data.ts` и `constants.ts`. В общий `shared/ui` выноси переиспользуемые примитивы, а не каждую карточку с бизнес-логикой.

Для лендинга используй композицию секций: `sections/Hero/Hero.tsx`, `sections/Benefits/Benefits.tsx`, затем явно перечисли их в странице. Не строй JSON-конструктор ради одной страницы. Не создавай цепочку container/view/controller/service без практической необходимости.

Внутри компонента держи hooks и состояния, получение данных, производные значения, обработчики, ранние выходы и JSX. Hooks вызываются безусловно. Небольшая функция или декоративный SVG может оставаться в том же файле; повторяющиеся данные и самостоятельные части UI выноси отдельно.

Локальную форму, открытие модалки и временный шаг держи в `useState`. Общий UI-state — в общем хранилище, серверные данные — в query-кэше. Не дублируй ответ сервера в state без задачи редактирования draft. Используй прямые `map/filter/reduce`; `useMemo/useCallback` добавляй для стоимости расчёта или стабильности зависимости, а не к каждой операции.

## UI и стили

Для прикладного UI предпочитай Tailwind в JSX. Объединяй классы через `cn = twMerge(clsx(...))`: базовые классы → условные классы/варианты → внешний `className`. Потребитель компонента должен иметь возможность переопределить оформление.

```tsx
className={cn(
  "flex items-center gap-3 rounded-xl p-3",
  isSelected && "bg-black text-white",
  isDisabled && "opacity-50",
  className
)}
```

Простые варианты оформляй явными условиями; устойчивую матрицу `appearance/size` можно вынести в CVA. Не вводи фабрику вариантов ради одной карточки. Для точного макета допустимы arbitrary values, градиенты, отдельные декоративные слои и inline SVG. Цвета, шрифты и размеры определяются интерфейсом, а не этим skill. Не собирай Tailwind-классы динамической строкой вроде `bg-${color}`.

Нативные UI-обёртки расширяй `ComponentProps`/`HTMLAttributes`, пробрасывай `...props`, `children`, `className` и ref, если он нужен API. `forwardRef` используй для ref-обёрток в React 18; не добавляй его ко всем предметным компонентам.

Диалоги, вкладки и переключатели собирай через Radix или готовые примитивы, если они доступны. Состояние открытой модалки выражай через `open/onOpenChange`; триггер может передаваться через `children`. Сохраняй нативную семантику: button для действия, link для перехода, label для поля, доступные названия для иконок.

Для сложной секционной вёрстки подходит пара `Name.tsx` + `Name.module.scss`. Импортируй модуль как `styles`, условные классы объединяй `clsx`. Вкладывай стили по структуре блока, медиапереопределения размещай рядом с изменяемым блоком. Не смешивай SCSS и Tailwind в одном блоке без причины.

Адаптивные значения задавай для нужных переходов макета; не копируй фиксированный набор breakpoints в каждую задачу. Для масштабируемого широкого макета допустимы vw, для мобильных экранов — точные px и safe area при необходимости. Анимации описывай явными `initial/animate/transition` или CSS keyframes, когда они нужны интерфейсу.

## Запросы, формы и состояния

- Если используется RTK Query, группируй endpoints по предметной области, расширяй базовый API через `injectEndpoints`, типизируй `build.query/build.mutation`, экспортируй сгенерированные hooks. Tags отражают данные, которые нужно обновить после мутации. Если выбран TanStack Query/Axios, сохраняй этот подход без миграции ради стиля.
- Сохраняй точные поля серверного контракта, в том числе snake_case. Не добавляй промежуточный слой переименования без задачи.
- Асинхронное действие оформляй как guard при pending → подготовка/проверка данных → `await mutation(payload).unwrap()` → действия после успеха → `catch`. В TanStack Query для такого потока используй `mutateAsync` либо callbacks, соответствующие сценарию.
- Не допускай повторного действия во время запроса: pending guard и disabled на соответствующей кнопке. Закрывай диалог и очищай ввод после подтверждённого успеха, если сценарий не задаёт другой переход.
- Известным кодам ошибок сопоставляй предметный текст, остальным — понятный fallback. Ошибку типа `unknown` сужай по реальной форме ответа; не маскируй её `any`, неподтверждённым cast или `@ts-expect-error`.
- Для короткой формы достаточно controlled inputs и `useState`. Для сложной формы с валидацией подходит React Hook Form + Zod, `z.infer`, ошибки около полей. Не добавляй эти зависимости к каждому input.
- Loading, error, empty и success — отдельные состояния. Skeleton повторяет геометрию загружаемого блока; loader действия остаётся в кнопке. Не заменяй ошибку бесконечной загрузкой. При обновлении данных сохраняй уже полезный контент, когда это подходит сценарию.
- Тексты и локализацию делай по требованиям интерфейса. Если используется i18n, переводи сообщения ошибок и валидацию вместе с остальным UI. Не добавляй i18n, Web3, платформенные SDK, звук или аналитику только ради соблюдения стиля.

## Примеры и проверка

Полные фрагменты находятся в [examples.md](references/examples.md): `cn`, Skeleton, ref-кнопка, debounce, группировка импортов, типизированный API и submit. Пример SCSS-секции с адаптивностью находится в [layout.md](references/layout.md). Это локальные части skill для иллюстрации конкретного приёма, а не обязательная подготовка перед каждой задачей. В них нет ссылок на внешние исходники.

В новом коде очищай таймеры и подписки, указывай зависимости эффектов и стабильные ключи динамических списков. Проверь типы, нужные состояния UI и доступные для задачи проверки. Сборка bundler без TypeScript-проверки не подтверждает корректность типов. Не добавляй тесты, повторяющие строки реализации; проверяй поведение там, где изменение этого требует.
