# Frontend в стиле Crypton

Воспроизводи способ организации и написания кода из рабочих проектов пользователя. Важны конкретные компоненты, прямые обработчики, близость логики к использующему её UI и существующие UI-примитивы. Не превращай задачу в внедрение новой архитектуры или универсального фреймворка компонентов.

## Сначала выбери локальный вариант

Прочитай инструкции репозитория, package.json, конфигурацию форматирования, соседнюю страницу/компонент и связанный API-файл. Для интерфейса также проверь локальные UI-примитивы, токены, ассеты и переводы. Достаточно релевантных файлов; не повторяй исследование всех исходных проектов при каждом вызове.

Порядок решений: явный запрос пользователя → правила и работающие контракты целевого проекта → ближайший аналог внутри него → образцы приоритетных проектов → вторичные образцы. Не позволяй более новому или более крупному проекту перекрывать заданные приоритеты.

| Контекст | Организация и оформление |
| --- | --- |
| Nutsfarm, id-frontend | `modules`, общие `components`, локальные `components/modals/hooks`; `shared/ui`, `redux/api`, `types`, Tailwind |
| events-front | `pages/<Page>/index.tsx` с локальными `components`, общие `shared`, `redux/api`, Tailwind |
| nutcracker-front-main | Компактные `components`, `components/Tabs`, `shared`, `redux/api`; не добавлять лишние слои |
| x-landing | `sections/<Name>/<Name>.tsx` + `<Name>.module.scss`, локальные `data.ts`, композиция секций в App |
| Academy | `pages` с вложенными компонентами/модалками, `shared/ui`, `shared/admin-ui`, `shared/typography`, RTK Query |
| academy-tma | Существующие `app/pages/widgets/features/entities/shared`, public API через `index.ts`, именованные экспорты, TanStack Router, Tailwind 4 |

Для нового React-приложения без других требований ориентируйся на простой вариант Nutsfarm/id-frontend: TypeScript, Vite, Tailwind, локальные UI-компоненты. Добавляй роутер, Redux/RTK Query, формы и другие зависимости по задаче, а не полным набором заранее. Для лендинга в духе x-landing выбирай секции и SCSS Modules. Версии зависимостей не копируй из снимка проектов.

Перед реализацией прочитай нужный раздел [patterns.md](references/patterns.md). Примеры формы кода находятся в [examples.md](references/examples.md). Обоснование приоритетов, реальные пути и исключения — в [evidence.md](references/evidence.md); открывай его при неоднозначности или необходимости найти первоисточник. Skill самодостаточен: отсутствие оригинальных репозиториев не мешает применить описанный стиль.

## Общий почерк

- По умолчанию — функциональный компонент `const Name = (...) => { ... }`, деструктуризация пропсов в аргументе, обычный JSX, понятное предметное имя. Не добавляй `React.FC` и явный тип возвращаемого JSX без причины.
- В основных проектах обычный компонент чаще заканчивается `export default Name`; общие UI-примитивы нередко имеют именованные экспорты. В academy-tma сохраняй именованные экспорты и существующие public API. Соседние файлы важнее этого умолчания.
- Небольшую форму пропсов пиши прямо в аргументе: `({ open }: { open: boolean })`. Для расширяемых или переиспользуемых пропсов подходит отдельный `NameProps`. Доменные модели и API-типы держи в принятом `types` или `entities/*/model`. Не вводи обязательные префиксы `I`/`T`: они различаются между проектами.
- Код и идентификаторы — на английском; объясняющие предметную логику комментарии могут быть на русском. Не добавляй комментарии, пересказывающие каждую строку.
- Именуй состояния `isOpen`, `isLoading`, `selectedId`, `activeStep`; несколько запросов различай алиасами: `data: profileData`, `isLoading: isProfileLoading`. Используй конкретные `handleSubmit`, `onSubmit`, `handleItemClick`, не навязывая один префикс всему репозиторию.
- Локальное состояние формы, открытие модалки и временные шаги держи в `useState`; общее состояние — в имеющемся slice; серверные данные — в существующем query-кэше. Производные значения считай рядом с компонентом. Не создавай отдельный hook для каждой короткой операции.
- Предпочитай явные условия, ранние выходы, `map/filter/reduce`, небольшие предметные функции. Выноси части UI по смыслу или при повторении; не создавай цепочку из container/view/controller/service для простого экрана.
- Используй `@/` для общих модулей, если alias настроен, относительные импорты — для локальных соседей. Импорты разделяй пустыми строками по смыслу; в academy-tma порядок задаёт `simple-import-sort`, в остальных не выдумывай единый строгий порядок.
- Базовое оформление: два пробела, двойные кавычки, без `;` в TS/TSX, перенос длинных JSX-пропсов. Конкретные trailing commas и сортировку Tailwind делегируй конфигурации проекта. В SCSS точки с запятой сохраняются.

## Реализация UI и данных

- В приложениях используй Tailwind в JSX; условные классы и внешние переопределения объединяй существующим `cn` (`twMerge(clsx(...))`). Порядок: базовые классы → условия/варианты → внешний `className`. Не создавай второй `cn` из-за отличающегося пути (`lib/cn` и `lib/classNames` оба встречаются).
- Используй реальные компоненты проекта: Button/LargeButton, Dialog/Drawer, Skeleton, Form/Input, типографику. Проверяй API: в id-frontend встречается `appearence`, в Nutsfarm — `appearance`, в academy-tma у Button обязательны `appearance` и `size`. Не исправляй публичные имена попутно.
- Выбирай существующие токены, шрифты, responsive-префиксы и изображения. Arbitrary values, градиенты, несколько декоративных слоёв и inline SVG допустимы для точного макета. Не переноси палитру или игровую кнопку Nutsfarm во все приложения.
- Для диалогов, переключателей и вкладок используй имеющиеся Radix-обёртки или принятый в модуле прямой Radix. Сохраняй `children`, `open/onOpenChange`, `asChild`, Portal и `data-[state=...]`, когда они предусмотрены API. Не заменяй готовую композицию самописной системой модалок.
- Расширяй существующий API через `injectEndpoints`, типизированные `build.query/build.mutation`, tags и экспорт сгенерированных hooks. В модулях с TanStack Query/Axios продолжай их схему; не мигрируй стек ради стилистического единообразия.
- Для мутаций с действиями после успеха используй `await mutation(payload).unwrap()` и `try/catch`; учитывай pending-состояние, блокировку повторного действия, локальную обработку известных ошибок и общий fallback. Существующий helper ошибок предпочтительнее нового.
- Покажи релевантные loading/error/empty/success состояния. Skeleton повторяет геометрию экрана; локальный loader остаётся внутри кнопки. Не скрывай ошибку бесконечной загрузкой или пустым `return null`.
- Сохраняй используемую локализацию: `useTranslation`/namespace, `t("Русская фраза")` либо ключи. В x-landing/events-front встречается прямой русский текст; не внедряй i18n без задачи. Новые переводы добавляй по принятой структуре.
- Motion, карусели, Telegram, звук, haptics и Web3 добавляй только для соответствующей задачи. Переиспользуй интеграции проекта; не считай их обязательной частью frontend-стиля.

## Границы подражания и проверка

Повторяй выразительный стиль, сохраняя корректность: не переноси подавления ошибок типов, закомментированные блоки, неочищаемые таймеры/подписки, отсутствующие зависимости эффектов, нестабильные ключи динамических списков и недоступные интерактивные элементы как личные предпочтения. Для новых обработчиков ошибок сужай `unknown` по фактической форме ответа; не маскируй проблему `any`, приведением типа или `@ts-expect-error`.

Перед завершением сравни результат с ближайшим образцом: размещение файлов, экспорт, пропсы, импорты, классы, API/hooks, тексты. Проверь доступность используемых токенов и ассетов, pending/error/empty-поведение и нужные размеры экрана. Выполни доступные проверки проекта, подходящие изменению. В ряде проектов `build` запускает только Vite: успешная сборка сама по себе не подтверждает типы; используй имеющийся `build-check` или подходящую проверку TypeScript. Если проверка недоступна или падает на существующей проблеме, сообщи это точно. Не устанавливай зависимости и не переделывай конфиги только ради применения skill.
