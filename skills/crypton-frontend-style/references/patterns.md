# Локальные варианты стиля

## Приложение: Nutsfarm / id-frontend / events-front / Nutcracker

Страница собирает предметные блоки; блоки хранят собственные небольшие компоненты. `modules/Tasks/components/buttons` в Nutsfarm и `pages/Quest/components/Inventory` в events-front — полезные ориентиры. Не превращай всё в глобальный UI-kit. Новую карточку конкретной задачи клади рядом с задачами, универсальную кнопку — в существующий `shared/ui` или `shared`.

Компонент обычно содержит hooks/состояния, получение данных, производные значения, обработчики, ранние выходы и JSX. Порядок hooks внутри этой группы различается; важнее читаемые зависимости и безусловный вызов hooks. Небольшие декоративные SVG/вспомогательные компоненты могут оставаться в том же файле. Большие повторяющиеся данные выносятся в `constants.ts`/`data.ts`.

### Пропсы и примитивы

Обычные компоненты принимают конкретные значения и callbacks; часто используют `children`, `className`, `open/onOpenChange`. Не передавай целый store или API-клиент ради одного значения. Нативные обёртки расширяют `React.ComponentProps<"button">`, `ButtonHTMLAttributes` или `ComponentPropsWithoutRef`.

В React 18 UI-примитивах встречаются `forwardRef`, `...props`, `displayName`. Поддерживай принятый способ проброса ref. Это не требование оборачивать каждый предметный компонент в `forwardRef`; в React 19 academy-tma встречается обычный компонент с `ComponentProps`.

Варианты оформляются в зависимости от сложности существующего компонента:

- Nutsfarm Button/LargeButton: явные условия по `appearance`, отдельные `contentClassName`, `shadowClassName`, декоративный слой под кнопкой, `group-active`.
- id-frontend Button: `cva` + `VariantProps`, собственный `isLoading`, prop `appearence`.
- Nutcracker OutlinedButton: компактная нативная обёртка с `cn`.
- academy-tma Button: `buttonVariants` в соседнем файле, обязательные `appearance` и `size`.

Не добавляй CVA для единственной карточки; не переписывай имеющуюся таблицу вариантов длинными условиями ради копирования другого проекта.

### Стили и адаптивность

`cn("база", condition && "условие", className)` — основной способ композиции. Для двух взаимоисключающих состояний обычный тернарный оператор уместен. Внешний `className` идёт последним. В Tailwind используй полные строки классов; не генерируй `bg-${color}` без существующего механизма обнаружения таких классов.

Сначала смотри локальную тему и соседний UI. В Nutsfarm много точных размеров мобильного интерфейса, branded fonts, radial/linear gradients, слоёв кнопок, `phone-sm` и safe area Telegram. В id-frontend есть `dark:` и условное масштабирование через `state.scale.value` + `3xl:*vw`. В events-front встречаются `phone`, `2md`, `extra`, clip-path и необычные шрифты. Это разные настройки, а не единый набор breakpoint-значений.

Не навязывай дизайн-токены каждому разовому значению: `[58px]`, точный цвет и сложный фон встречаются в авторском коде. При этом существующий токен предпочтительнее его дубликата. Применяй значения по макету и окружению, а не случайную палитру из образца.

Ассеты импортируются из `assets`; SVG бывает URL для `<img>` или React-компонент через `?react`. В x-landing старый синтаксис SVGR `ReactComponent as ...`; смотри установленную конфигурацию. Не добавляй библиотеку иконок вместо локальной коллекции без необходимости.

### API и состояние

Для RTK Query найди общий `api`/`baseApi` и доменный endpoint-файл. Сохраняй базовый URL, авторизацию, refresh-логику и форму ответа. Новые endpoints подключаются через `injectEndpoints`, а hooks экспортируются из файла либо public API сущности. Укажи `providesTags/invalidatesTags` по реальным зависимым данным; новый tag добавь в базовый API, если требуется. Формат имён tag сохраняй: `CURRENT_USER`, `UserProfile`, `Me` — разные локальные контракты.

У простого запроса пропсы аргумента могут быть inline-объектом; большие payload/response — отдельные interface. Не переименовывай серверные snake_case-поля в camelCase без существующего преобразования.

Для действия: guard при pending → вызов mutation → `.unwrap()` → нужное обновление UI/закрытие модалки/toast. Ошибку обрабатывай по контракту проекта, а не по скопированному из другого приложения `error.data.code` или `detail.code`. Известный code получает предметный текст, остальные — fallback. Формы/шаги сохраняют введённые данные при ошибке, если сценарий не требует другого.

Короткие controlled inputs могут использовать `useState` и trim в submit. Если модуль уже использует React Hook Form и Zod (например, EmailLogin), продолжай `useForm`, `zodResolver`, `z.infer`, `FormField`, `FormMessage`. Не тащи этот набор в каждый переключатель или простую строку поиска.

Не копируй response в Redux slice или локальное состояние без необходимости редактируемого draft. Для общего UI-состояния используй `useAppSelector/useAppDispatch` и существующие `createSlice`/`PayloadAction`. Расчёты оставляй прямыми; `useMemo/useCallback` — по зависимости, стоимости или стабильности, не как обязательный шаблон.

## Лендинг: x-landing

Этот раздел нужен для создания/изменения лендинга в стиле x-landing. Сам факт слова «лендинг» не даёт основания мигрировать существующий Next/Tailwind проект на SCSS.

Типичная структура:

```text
src/
  App.tsx
  index.scss
  _mixins.scss
  sections/
    index.ts
    Team/
      Team.tsx
      Team.module.scss
      teamData.ts
  components/
    MemberModal/
      MemberModal.tsx
      MemberModal.module.scss
```

App явно перечисляет секции в порядке страницы. Секция имеет `<section id="..." className={styles.section}>`, заголовки, конкретные изображения и нужную разметку. Комбинация классов — `clsx(styles.card, active && styles.active)`. Статические списки — массивы рядом с секцией и `.map`; не создавай универсальный JSON-конструктор лендинга.

SCSS-файл импортирует `@use "../../mixins"`; стили вложены по структуре блока, встречаются `_left`, `_right`, `&:hover`, `&:nth-child`. Медиапереопределения расположены около соответствующего свойства/блока.

Исходные mixins: `desktop` от 1921px, `laptop` до 1300px, `small-laptop` до 1110px, `big-tablet` до 900px, `tablet` до 768px, `small-tablet` до 600px, `phone` до 480px, `small-phone` до 365px. База преимущественно px; для широкого desktop применяется vw относительно 1920px. Это образец конкретного лендинга: в новом проекте применяй его только при выборе этого варианта и подходящем макете.

Анимации появления: `useInView({ threshold, triggerOnce: true })`, `motion.*`, явные `initial/animate/transition`, отдельные ref для смысловых групп. Скролл/бесконечные декоративные движения могут быть в CSS keyframes. Не добавляй анимации каждому узлу по умолчанию и не скрывай основной контент навсегда, если наблюдатель не сработал.

## Academy и academy-tma

В Academy поддерживай текущие `pages`, локальные modal/editor hooks и разные наборы `shared/ui`, `admin-ui`, `typography`. Новая форма не должна обходить местные Label/Input/Caption и диалоговые обёртки. Здесь есть helper `getApiErrorCode`, константы `API_ERRORS`, RHF/Zod и осмысленные тесты утилит: переиспользуй их по месту.

В academy-tma сохраняй существующие слои, экспорты через `index.ts`, `import type`, предметные типы в `entities/*/model`, endpoints в `entities/*/api`, инфраструктуру в `shared/api`. Межсущностные импорты через имеющийся `@x` поддерживай там, где это уже принято. Не создавай пустые слои или отдельную сущность для каждого декоративного блока.

Роутинг в просмотренном academy-tma описан кодом через `createRoute` и `getParentRoute`; не предполагай файловую генерацию маршрутов только по наличию TanStack Router. Сохраняй местные route constants/search-параметры. Tailwind 4 читает тему из CSS; не добавляй автоматически конфигурацию Tailwind 3 из Nutsfarm.

В этих проектах есть более современные named exports, типовые API-помощники и тесты. Это локальные варианты, а не указание переписать остальные проекты под них.
